# IdentificationIntegratorOnA4

スキャンした身分証画像から身分証部分を検出・切り出し、**印刷用の物理サイズを維持したまま**
白背景の A4 PNG に配置する、Windows 向けローカル完結デスクトップアプリ。

要件定義: [`CLAUDE_CODE_SPEC.md`](./CLAUDE_CODE_SPEC.md)

> **本書の位置づけ**
> 仕様書 §1 / §11 に基づく **実装開始前の設計提案** です。技術構成・依存関係・画像処理方式・
> 安全上限とその根拠・開発／テスト／Windows 配布手順をここに定義し、以降の実装はこの設計に従います。

---

## 0. 絶対に守る原則

| # | 原則 | 実装上の担保 |
|---|------|--------------|
| 1 | 画像・メタデータ・ログを**ネットワークへ送信しない** | レンダラは `contextIsolation: true` / `sandbox: true`、CSP で `connect-src 'none'`。HTTP クライアント依存を持たない |
| 2 | OCR・クラウド API・分析 SDK・テレメトリーを**実装しない** | 依存許可リストを CI で検証 |
| 3 | 入力ファイルを**削除・移動・更新・上書きしない** | 入力パスは読み取りモードでのみ open する。書き込み系 API は「出力ルート配下か」を判定するガード関数を必ず経由する |
| 4 | 出力先配下を**必ず走査から除外** | 走査時に出力ディレクトリの実パス（`fs.realpath`）配下を判定して除外。シンボリックリンク経由の再入も遮断 |
| 5 | ログに**個人情報を残さない** | ログ API は「入力ルートからの相対パス・結果コード・理由コード」のみを受け取る型に制限。画像バッファを渡せない API 設計にする |

## 1. 技術構成（仕様書 §11-1）

### 1.1 採用スタック

| 層 | 採用 | 理由 |
|----|------|------|
| デスクトップシェル | **Electron**（最新 stable 系を実装時に固定） | 仕様書の候補。Windows 単体配布が容易で、ネイティブ画像ライブラリを同梱できる |
| 言語 | **TypeScript 5**（`strict: true`） | 型検査を品質ゲートに組み込む |
| UI | **React 18** + CSS Modules | 確認画面は表形式＋状態管理が中心のため、軽量構成で足りる |
| ビルド | **electron-vite** | main / preload / renderer を 1 設定でビルドでき、HMR も効く |
| パッケージング | **electron-builder** | NSIS インストーラと portable zip を同時生成。ネイティブ依存の asar 展開制御が確実 |
| テスト | **Vitest** | Vite 構成と共有。画像処理ロジックを Electron 非依存で実行できる |
| Lint / 整形 | **ESLint**（typescript-eslint）+ **Prettier** | |

### 1.2 プロセス責務の分離

```
+----------------------------------------------------------+
| renderer (React) - sandbox:true / nodeIntegration:false   |
|   設定画面・確認画面・進捗画面。fs も net も触らない        |
+---------------------^------------------------------------+
                      | contextBridge で公開する型付き IPC のみ
+---------------------+------------------------------------+
| preload - window.api の薄いラッパ。任意チャネルは通さない  |
+---------------------^------------------------------------+
                      | ipcMain.handle / webContents.send
+---------------------+------------------------------------+
| main - ウィンドウ管理／フォルダ選択ダイアログ／設定永続化   |
|        ジョブ統括・キャンセル・一時ディレクトリの生涯管理    |
+---------------------^------------------------------------+
                      | worker_threads (MessagePort / Transferable)
+---------------------+------------------------------------+
| worker pool - 画像 I/O・カード検出・透視補正・A4 合成      |
|               sharp と OpenCV(WASM) はここにだけ存在する   |
+----------------------------------------------------------+
```

重い処理を worker に閉じ込めることで、100 Mpx 級の画像処理中も UI がフリーズしません。
`utilityProcess` ではなく `worker_threads` を選ぶのは、**Transferable な `ArrayBuffer` を
コピーなしで受け渡せる**ためです（サムネイル数十枚の転送コストが実測で効いてきます）。

### 1.3 ディレクトリ構成（予定）

```
src/
  main/          Electron main。ウィンドウ・IPC・設定・ジョブ統括
  preload/       contextBridge 定義
  renderer/      React UI（設定 / 確認 / 進捗）
  worker/        画像処理ワーカー本体
  core/          ★ Electron 非依存の純粋ロジック（テストの主戦場）
    scan/          フォルダ再帰走査・除外判定
    detect/        背景推定・マスク・輪郭・候補スコアリング
    geometry/      四隅整列・透視変換パラメータ
    dpi/           DPI 正規化と mm 換算
    layout/        A4 レイアウト・ページ分割・出力順
    naming/        連番採番・衝突回避
    logging/       非機微ログ
  shared/        main / renderer 共有の型・定数
tests/
  unit/          core の単体テスト
  fixtures/      ★ 合成画像の「生成コード」（画像そのものはコミットしない）
```

`core/` を Electron から独立させるのが設計の要です。仕様書 §10 が要求する自動テスト
（DPI 換算・ページ分割・2列x4行配置・回転・命名衝突）は、すべて `core/` に対する
純粋関数テストとして、Electron を起動せずに実行できます。

## 2. 画像処理ライブラリと Windows 配布時の依存関係（仕様書 §11-2）

### 2.1 採用: sharp（入出力）＋ OpenCV WASM（検出）の二段構え

| 用途 | ライブラリ | 選定理由 |
|------|-----------|----------|
| 復号・Exif 回転・ICC・切出し・A4 合成・PNG 出力（DPI 付き） | **sharp**（libvips） | Windows x64 のビルド済みバイナリを配布。TIFF/PNG/JPEG を高速かつ低メモリに扱える |
| 二値化・モルフォロジー・輪郭抽出・透視変換 | **@techstark/opencv-js**（OpenCV の WASM ビルド） | **ネイティブビルド不要**。Windows 配布で最大の地雷である OpenCV のリンク問題が発生しない |

**`opencv4nodejs` を採用しない理由**: OpenCV 本体のビルドまたは事前配置が必要で、
Electron の ABI に合わせた `electron-rebuild` も要ります。CI・開発者マシン・配布先の
3 箇所で同じ問題を踏むため、コストが利得を上回ります。

**sharp が Electron で安全な理由**: sharp のビルド済みバイナリは **Node-API（ABI 安定）** に対して
コンパイルされており、Electron 側の V8/Node ABI が変わっても再ビルドが不要です。
これが `electron-rebuild` を要するネイティブ OpenCV との決定的な差です。

### 2.2 Windows 配布時の依存関係の扱い

1. **導入**: `npm i sharp` で `@img/sharp-win32-x64`（libvips 同梱）が入ります。
   CI が Linux の場合はクロス取得のため `npm i --cpu=x64 --os=win32 sharp` を併用します。
2. **asar 展開**: ネイティブ `.node` と DLL は asar 内から dlopen できません。electron-builder に次を指定します。

   ```jsonc
   {
     "asar": true,
     "asarUnpack": ["**/node_modules/sharp/**", "**/node_modules/@img/**"]
   }
   ```

3. **WASM の同梱**: `@techstark/opencv-js` は WASM バイナリを `dist/opencv.js`（約 10.8 MB）へ
   **埋め込んだ単一ファイル**として配布されており、`.wasm` サイドカーがありません。
   そのため asar 展開の追加設定も実行時のファイル読み込みも不要で、**ネットワーク取得も一切発生しません**。
   （検証済み: OpenCV 4.12.0 / Node 20 で初期化 101 ms、`findContours` / `warpPerspective` / `cvtColor` 利用可）
4. **配布形態**: NSIS インストーラと portable zip の 2 種を生成します。
   libvips は静的同梱のため、Visual C++ 再頒布可能パッケージへの追加依存はありません。
5. **署名**: 本リポジトリではコード署名証明書を扱いません。未署名配布では初回起動時に
   SmartScreen 警告が出る旨を配布手順に明記します。

## 3. 画像処理方式

### 3.1 パイプライン（1 画像あたり）

```
(1) メタデータのみ読取り   sharp(file).metadata()          <- 復号前に安全上限を判定
(2) 検出用プロキシ生成     .rotate().flatten(#fff).resize(長辺1600).raw()
(3) 背景色推定            外周リングの Lab 中央値
(4) 差分マスク            dE(CIE76) と dL の適応的閾値
(5) 形態学処理            close(5x5) -> open(3x3) -> 穴埋め
(6) 輪郭抽出・候補評価     面積 / 矩形度 / アスペクト比 / 端接触ペナルティ
(7) 四隅決定             approxPolyDP(4点)、失敗時は minAreaRect
(8) 座標を原寸へ写像       scale = 原寸長辺 / 1600
(9) 原寸切出し            sharp(file).rotate().extract(四隅の外接矩形)  <- ここだけ原寸
(10) 透視変換             OpenCV warpPerspective（入力は (9) の外接矩形のみ）
(11) DPI 正規化 -> mm 換算 -> A4 セルへ等倍中央配置
```

**この設計の肝は (9) です。** 検出は 1600px のプロキシで行い、原寸を扱うのは
**カード外接矩形の範囲だけ**です。600dpi のカード外接矩形は約 2100x1400px（約 3 Mpx）に過ぎず、
入力が 160 Mpx でも JS 側・WASM 側のピークメモリはカードサイズに支配されます。
JPEG では sharp の shrink-on-load（1/2・1/4・1/8 復号）が効くため、(2) のコストはほぼ無視できます。

### 3.2 検出の詳細

- **背景推定**: 画像外周 4% のリング画素を Lab に変換し、チャンネルごとの**中央値**を採ります。
  平均ではなく中央値なのは、カードが画像端に接している場合でも背景推定が汚染されないためです。
- **マスク**: `dE > t` または `|dL| > tL`。`t` は固定値ではなく
  `t = max(12, median(dE) + 3 * MAD(dE))` として、白背景・淡色背景の双方に適応させます。
- **候補スコア**: `0.40*矩形度 + 0.25*アスペクト適合 + 0.25*正規化面積 + 0.10*(1-端接触率)`。
  矩形度 = `contourArea / minAreaRect.area`。
- **信頼度の判定**:

  | 状態 | 条件 | 確認画面の扱い |
  |------|------|----------------|
  | 検出成功 | 最良スコア >= 0.75 かつ次点との差 >= 0.15 | そのまま採用 |
  | 要確認 | 0.55 <= 最良スコア < 0.75、または有力候補が複数 | 警告付きで表示。利用者が種別を確認のうえ続行できる |
  | 検出失敗 | 最良スコア < 0.55、または候補なし | 出力対象から除外し理由を表示 |

- **アスペクト比で書類種別を自動判定しません**。ID-1 カードは 85.6/54.0 = **1.585**、
  パスポート見開きは 176/125 = **1.408** と近接しており、誤判定が避けられないためです
  （仕様書 §2 のとおり種別は利用者が確認画面で選択します）。スコアには
  「1.1〜2.6 の範囲内か」という緩い適合度としてのみ寄与させます。
- **Exif 回転**: `sharp().rotate()`（引数なし）で Exif Orientation を適用します。
  **プロキシと原寸切出しの両方で必ず適用**し、座標写像は回転後の寸法を基準に行います
  （回転適用漏れは座標ズレの典型的な原因です）。
- **透過 PNG**: `.flatten({ background: '#ffffff' })` を検出前・出力前の両方で適用します。
- **壊れた ICC**: 1 回目は ICC 変換ありで復号し、失敗したら ICC を無視して再試行します。
  それでも失敗した画像だけを理由付きで除外します（アプリは停止しません）。

### 3.3 DPI と物理サイズ（仕様書 §6）

- sharp の `metadata().density` から DPI を取得します（JPEG=JFIF / PNG=pHYs / TIFF=XResolution）。
- **有効判定**: 有限の数値かつ `100 <= dpi <= 2400`。範囲外・欠損・0 は無効として **300dpi** で扱い、
  確認画面に `DPI情報なし・300dpiとして配置` を表示します。
- 物理サイズ `mm = px / dpi * 25.4`、A4 上の配置画素数 `px_A4 = mm / 25.4 * 300`。
- **縮小は一切しません。** 枠に収まらない場合は出力対象から除外し、理由を表示・記録します（仕様書 §6）。
- 出力 PNG には pHYs を書き込みます（`300 dpi = 11811 px/m`）。sharp の `density: 300` 指定で出力されます。

### 3.4 A4 レイアウトの実数値（仕様書 §7）

| 項目 | px @300dpi | mm |
|------|-----------|-----|
| A4 全体（縦向き） | 2480 x 3508 | 210.0 x 297.0 |
| 全周セットバック | 118 | 10.0 |
| 印刷可能領域 | 2244 x 3272 | **190.0 x 277.0** |
| セル（2列 x 4行） |  1122 x 818 | 95.0 x 69.3 |
| ID-1 カード（参考） | 1011 x 638 | 85.6 x 54.0 |
| セル内の余白（参考） | 左右 55.5 / 上下 90 | 左右 4.7 / 上下 7.6 |
| パスポート見開き 90 度回転後（参考） | 1476 x 2079 | 125.0 x 176.0 |

印刷可能領域の実測値が仕様書の `190 x 277 mm` と一致することを確認済みです。
ID-1 カードもパスポート見開きも、それぞれの配置枠に**縮小なしで収まります**。

### 3.5 出力順（仕様書 §11-4）

推奨案（入力相対パスの自然順を維持）を採用します。

```
自然順ソート -> 順に走査
  - 身分証カード -> カードバッファへ追加。8 枚たまったらページ確定
  - パスポート   -> その時点のカードバッファを（8 枚未満でも）ページ確定して出力
                    -> 続けてパスポート単独ページを出力 -> バッファを空にして継続
最後に残ったカードバッファをページ確定
```

これにより「パスポートの前後でカードページを確定して連番化」となり、
出力ファイルの連番順＝入力の自然順という直感的な対応が保たれます。

### 3.6 出力ファイル命名と衝突回避（仕様書 §4）

1. `<出力ルート>/A4Integrate` を作成します（既存ならそのまま利用）。
2. 既存の `integrated_A4_(\d{3,}).png` を走査し、最大番号 `n` を得ます。
3. `n+1` から採番し、書き込みは `fs.open(path, 'wx')`（**排他作成**）で行います。
   `EEXIST` なら番号を進めて再試行します。手順 2 だけでは他プロセスとの競合で
   上書きが起こり得るため、排他作成を最終防壁とします。

## 4. 安全上限とメモリ見積もり（仕様書 §9 / §11-3）

### 4.1 上限値

| 上限 | 値 | 根拠 |
|------|-----|------|
| 最大ファイルサイズ | **300 MB** | A4 全面 600dpi・16bit・非圧縮 TIFF が約 34.8 Mpx x 6 B = **約 209 MB**。これを包含しつつ、明らかな異常ファイルは弾ける水準 |
| 最大幅・高さ（各辺） | **30,000 px** | A4 長辺 297mm を 2400dpi で読むと 28,063 px。極端なアスペクト比の圧縮爆弾も同時に遮断できる |
| 最大総画素数 | **160 Mpx** | パスポート見開き(176x125mm) 1200dpi = 49 Mpx、A4 全面 1200dpi = 139 Mpx。実用的な最高解像度スキャンを包含する最小水準 |
| 同時処理数 | **max(1, min(4, CPU数-1))** かつ **処理中の総画素 <= 200 Mpx** | 下記 4.2 |

上限値は `src/shared/limits.ts` に集約し、テストからも参照します。

### 4.2 メモリ見積もりと対策

**判定を復号より先に行う**のが第一の対策です。`sharp().metadata()` はヘッダのみを読むため、
上限超過ファイルは**一度も復号せずに**除外できます（これが圧縮爆弾対策そのものです）。

復号する場合のピーク見積もり（最大 160 Mpx 入力・1 画像あたり）:

| 段階 | バッファ | 概算 |
|------|---------|------|
| (2) プロキシ生成（libvips 逐次処理） | libvips 内部タイル | 〜400 MB（RSS。全画素を同時展開はしない） |
| (2) プロキシ raw | 1600 x 1131 x 3 B | **5.4 MB** |
| (9) 原寸切出し（カード外接矩形のみ） | 600dpi で約 3 Mpx x 3 B | **9 MB** |
| (10) OpenCV WASM（(9) の入力のみ） | 入出力 Mat 2 枚 | **〜25 MB** |
| (11) A4 キャンバス | 2480 x 3508 x 3 B | **26 MB** |

**ワーカーあたりのピーク RSS は最悪ケースで約 600 MB**、通常（30 Mpx 級）で約 150 MB です。
「処理中の総画素 <= 200 Mpx」というピクセル予算スケジューラにより、160 Mpx の巨大画像は
事実上 1 枚ずつ、通常サイズなら 4 並列で流れます。結果として
**アプリ全体のピークを約 1.5 GB 以内**に抑えます（8 GB 機で安全域）。

OpenCV WASM のヒープは上限 512 MB で初期化し、WASM へ渡す Mat には
「カード外接矩形のみ・40 Mpx 以下」というガードを設けます。WASM の 4 GB アドレス空間制限は、
原寸全体を WASM へ渡さない設計により構造的に回避されます。

### 4.3 上限超過時の挙動（仕様書 §9）

停止せず、当該画像だけを除外して継続します。確認画面と処理結果に次を表示します。

- 入力ルートからの**相対パス**
- **超過した制限**（例: `総画素数 210 Mpx が上限 160 Mpx を超過`）
- **利用者がとれる対応**（例: `スキャン解像度を 600dpi 以下にして再スキャンしてください`）

### 4.4 一時ファイルと機微データの扱い（仕様書 §11-5）

**通常経路では一時ファイルを作りません。** サムネイルは worker 内で WebP（長辺 240px）へ
エンコードし、`ArrayBuffer` を Transferable として main 経由でレンダラへ渡します。
レンダラは `Blob` から `createObjectURL` して表示し、行の破棄時に `revokeObjectURL` します。
ディスクにもネットワークにも出ません。

一時ディレクトリが必要になった場合のみ `fs.mkdtemp(path.join(app.getPath('temp'), 'a4int-'))` で
**アプリ専用に**作成し、レジストリに登録して次のすべてで削除します。

- ジョブ成功 / ジョブ失敗 / 利用者による中止 / `before-quit` / `process.on('exit')`
- さらに起動時に、24 時間以上前の `a4int-*` を掃除します（異常終了時の取りこぼし対策）

削除対象は**アプリ自身が作成した `a4int-*` ディレクトリに限定**し、それ以外のパスは削除しません。

## 5. 確認画面（仕様書 §8）

各行に表示する項目:

| 列 | 内容 |
|----|------|
| サムネイル | 切り出し結果（メモリ上の WebP。検出失敗時は元画像の縮小） |
| 相対パス | 入力ルートからの相対パス |
| 検出状態 | 検出成功 / 要確認 / 検出失敗 |
| DPI | 埋め込み値、または `DPI情報なし・300dpiとして配置` |
| 配置サイズ | A4 上の配置サイズ（mm、小数第 1 位） |
| 除外理由 | 該当時のみ（上限超過・枠超過・検出失敗・復号失敗など） |
| 種別 | `身分証カード` / `パスポート見開き` の選択（既定は `身分証カード`） |

- **出力は確認画面で「出力開始」が押された後にだけ生成します。**
- 「中止」で出力を一切作成せずに終了します。処理中の中止は `AbortSignal` を worker まで伝播させます。
- 出力開始後は、進捗・成功ページ数・除外画像と理由・**出力フォルダを開く**操作を表示します。
- 入力画像が 0 枚の場合は処理を開始せず、理由を明示したモーダルを表示します。

### 6.4 テスト方針（仕様書 §10）

**実在する身分証・個人画像・個人情報は一切使いません。** テスト画像はすべて
`tests/fixtures/` の**生成コード**から実行時に合成し、生成物はコミットしません
（`.gitignore` で画像拡張子を既定除外済みです）。

生成する合成ケース: 白／灰／淡色背景、色差の大きい長方形、傾き、影、ノイズ、
複数候補、検出不能、破損ファイル、DPI 有無、Exif 回転、透過 PNG、巨大画像。

自動テストの対象:

- カード検出・透視補正の幾何精度（既知の四隅に対する誤差）
- DPI 換算（有効値・欠損・範囲外の 3 系統）
- ページ分割と 2列 x 4行 の配置座標
- パスポートの 90 度回転・単独ページ・混載しないこと
- 出力フォルダの走査除外（シンボリックリンク経由を含む）
- **入力不変**（処理前後のファイルハッシュと mtime の一致）
- 出力名の衝突回避（既存連番あり・並行書き込み）
- **ログの非機微性**（生成ログに絶対パス・画像データが含まれないこと）
